Adding Semantic Context to Types

This post explores some ideas around types containing semantic context. It's a thought exercise more than an endorsement of a certain programming style. The code examples use Rust syntax, but the ideas themselves aren't specific to Rust.

Suppose we're writing some networking code and we need to represent an IPv4 address. Which of the following data representations would you generally tend towards?

// 1 - Primitive types, like a fixed-size array or tuple of u8
let ipv4_addr = [127, 0, 0, 1]; // or (127, 0, 0, 1);

// 2 - The newtype pattern (or something like it) to hide the primitive
struct Ipv4Addr([u8; 4]); // or (u8, u8, u8, u8)

// 3 - Using a struct with primitive fields
struct Ipv4Addr { octets: [u8; 4] }

// 4 - Using a struct with user-defined fields
struct Octets([u8; 4]) // or (u8, u8, u8, u8)
struct Ipv4Addr { octets: Octets }

// 5 - Using a struct with explicit fields for each octet
struct Ipv4Addr { o1: u8, o2: u8, o3: u8, o4: u8 }

The answer largely depends on programming pedigree, right? Dynamic-typing enthusiasts probably tend towards something like options 1 or 5, while the statically-typed folks might lean into option 4 or beyond. (I'm using broad strokes here to make a point, of course there's nuance.)

What's the Difference?

The first choice (option 1) uses the type to determine structure only. Semantic information is pushed completely into the surrounding context, along with the notion of what you "should" and "should not" do with the data.

The alternative is to put more or less amounts of semantic context into the type itself. Instead of exposing primitive data structure(s), it gets wrapped with a name bolted onto it. Everywhere the data goes, the name goes with it.

Context isn't just a name, though. Most languages let you affix algorithms ("methods") directly onto a type, indicating the range of operations intended to be performed on that type. This cuts both ways: styles that tend to push context out of the type and into e.g. variable names also lose the ability to be explicit about what a "valid" operation is, at least up to a certain point. Consider the following:

fn do_stuff(user_id: String) {
    // ...
}

Even with a typed function signature, we still can't really tell what a user ID is here. Is it a UUID? If so, what version? Is it formatted (with "-") or not? If not a UUID, how many characters should it have? Is it hex, or ascii, or is it empty for some reason?

And apart from structure, what should we be able to do with this thing? Here's the list of methods for Rust's String type, are they relevant for a user ID? Should I be able to truncate it, or pop the last char?

We might be able to tell in a local context, but when something like this drifts across modules in a 100k+ line codebase we're inevitably going to start hurting. Hopefully it's not something that gets mutated along the way and undergoes some internal state transitions...

When to Stop

But we know this. Type systems have more or less won, at least to some extent in team-based programming. If that's the case, and moving some semantic context into types is the right answer, how much is too much?

To be frank, I'm not exactly sure, but I'm also pretty sold on the idea of using a type's intended public interface as the guiding principle here. Just because your type is backed by a four-byte array doesn't mean it should be exposed as a four-byte array. A decent defensive stance is to assume that anything public will be used, and so only make public what you intend to be used.

Off the Deep End

We could stop here. We probably should stop here. We won't stop here.

Practical advice ended at the previous section. The remaining stuff is...different.

Suppose we're determined to push all context into the type system and we're not satisfied until:

  1. All types passed around in our application are user defined (by us, not externally),
  2. When we talk to external code, we wrap and unwrap our types accordingly,
  3. We only use a type if its API matches our immediate need. If the structure matches but the API doesn't, we have to [un]wrap it (even if it's our own type).

For example:

// some_external_crate.rs
fn do_more_stuff() -> Ipv4Addr {
    // ...
}

// our_code.rs
let client_addr = do_more_stuff(); // wrong
let client_addr = ClientAddr::from(do_more_stuff()); // right, kind of

Ok, now what? This follows our rules, but we have that pesky variable name. If we're pushing context into the type, the name is redundant. Can we get rid of it? Well, it depends what we want to do. If we're sticking with Rust (or something like it) then our options are limited. Interesting things can happen if we commit ourselves to using From/Into for transformations between types (IMO an overlooked near-killer feature of Rust), but that's maybe a topic for another time.

Instead, let's look at some prior art: Forth. In Forth, variables are more the exception than the rule. Instead of explicit assignment, data gets pushed to and pulled from an implicit stack, like so:

\ Push two numbers onto the stack
2 3

\ Add them together
+

\ Print the result (5)
.

The stack exists across functions, so there's no explicit parameter passing:

\ Define a "square" function
: square
    dup
    *
;

\ Push 5 onto the stack, call square, then pop and print the result
5 square .

One downside surfaces when you need to use items on the stack but in a different order than they've been pushed. This unfortunately is a possibility whenever you modify code that changes the stack. This doesn't happen in e.g. Rust (or most other languages) because you refer to variables by name, like a map. In Forth, you'd have the manually reorder the element's stack position to get it where you want. There are functions for e.g. swapping the top two elements, duplicating elements, swapping an element at position n with the top, etc.

Experienced Forth programmers work to optimize the flow of functions so the inputs and outputs flow together nicely, but the issue is never completely obviated. Regardless, the interesting bit here is that a dominating feature of Forth is the implicit stack and the general elimination of explicit variables (although they are still supported when required).

Combining Approaches

Can we take inspiration from Forth's stack approach to remove our own variables? What would that even look like?

If you haven't guessed already, I'm not a fan of the stack manipulation stuff, so that would have to be resolved if possible. In lieu of a stack, I propose using an implicit key-value structure, much like existing contexts in a mainstream language. The only differences are that, when a function returns, its return values are implicitly added to the caller's context instead of being explicitly assigned to a variable, and when a function is called, the arguments are implicitly pulled from the caller's context and passed to the callee.

How does this work? Well, we made a bunch of ho-hum earlier about pushing as much semantic context into the type as possible, and this is where it comes into play. Since types now contain the information that would normally be carried in a variable name, we can just pass around data by referring to its type (and implicitly so at that, a la Forth).

In a model like that, the following pseudo-code kind-of makes sense:

This isn't fully baked, just off-the-cuff thought-stuff. 
/// Some connection statistics
struct Stats {
    Latency,
    ConnectionCount
}

fn get_connection_count(ClientAddr) -> ConnectionCount {
    // ...
}

fn get_latency(ServerAddr) -> Latency {
    // ...
}

fn do_stuff(ClientAddr, ServerAddr) -> Stats {
    // call do_more, then call do_even_more, then collect into Stats and return

    do_more | do_even_more |= Stats
}

If you squint and allow some looseness for the sake of ideation then this potentially makes sense. Variable names are gone without losing contextual information, and you get flow-like algorithms without a bunch of stack manipulation stuff to deal with the ordering issue.

Final Remarks

There's still some obvious things to work out, though. For one, we're assuming this hypothetical language makes creating types easy, and has facilities for both allowing and restricting piecemeal access to an underlying type if needed. For example, consider the case where a helper function is reused twice in the same context. Its return type can't change, and the caller can't store two of the same types in its context, so we'd need a way to wrap the type while still allowing normal API access to it. We'd also need to "unwrap" our outer layer when passing it to a function that expects the underlying type.

At any rate, it's at least been a fun thought exercise. I might explore this more concretely, but if you're interested in this sort of thing feel free to reach out on GitHub. Thanks for reading!
